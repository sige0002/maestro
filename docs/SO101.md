# Maestro on SO101 (MuJoCo)

The default entrypoint is `maestro.so101.agent_runner`. SO101 and the original
Franka runner use the same `maestro.agent.VLMCodeExtractor`, `plan_first_step`
and `execute_plan_loop`. Executed code, errors, measured state and fresh images
feed the next model decision. Variables persist across steps. The agent composes
perception, grasp, transport, release, retreat and return itself; no task-level
`pick_place_cube` macro is exposed.

This is an SO101 adaptation, **not a complete reproduction of the paper's
Franka stack or its benchmark results**.

| Component | SO101 backend |
| --- | --- |
| Code generation, execution, visual replanning | Shared upstream Maestro harness and schemas |
| Pointing and numbered-point part selection | Original Maestro VLM clients |
| Segmentation | Official SAM 3.1 unified text/visual prompting; no GroundingDINO |
| Geometry helpers and scan cache | Shared with the Franka API |
| Depth | RGB-only Depth Anything V2 Metric Indoor Large; explicit MuJoCo sensor reference mode |
| Grasp proposals | RGB-D geometry and SO101 reachability, not GraspGen |
| Motion | SO101 IK, sampled collision checks and RRT, not cuRobo |
| Completion | Model assessment plus measured home-state guard |

Objects move through physical finger contacts. No object attachment or
teleportation is used. The agent reads RGB/joint observations and estimates depth, not
dynamic object poses from simulator state. Static robot/cell geometry comes
from the shared SO101 model. Separated compact tabletop objects are supported;
arbitrary objects, touching assemblies and physical execution are not validated.
Estimated depth approximates the visible surface; a point occluded by the arm can be on a
finger. Final object localization should happen after the arm returns clear.

## Setup

Run from Maestro; adjust `SO101_ROOT` if SO101 is not a sibling repository.
Stop other command publishers using the SO101 launcher before starting a trial.

```bash
export SO101_ROOT="../so101"
cp config/so101.example.yaml config/so101.yaml
make -C "$SO101_ROOT" mujoco-build
SIM_CUBE_LAYOUT=mixed "$SO101_ROOT/so101" mujoco up --force-recreate --no-deps
docker compose -f compose.so101.yaml build
```

`mixed` places a red cylinder, blue rectangular bar and green cube beside a
tray. `default` and `rotated` retain the legacy cube scenes. RGB and `32FC1`
metric depth use matching timestamps. `MAESTRO_ROS_DOMAIN_ID` defaults to 71.

### SAM 3.1 (default)

Use Meta's current [SAM 3.1 release](https://github.com/facebookresearch/sam3/blob/main/RELEASE_SAM3p1.md),
which integrates text-conditioned detection and mask generation. GroundingDINO
and SAM 1 are not used by this SO101 backend. Official source is pinned to
`f92a5efc4001ebfe9d050d43e61f6fb10e02d73c`; official `facebook/sam3.1`
weights are pinned to `daa63191845a41281374e725f4c9e51c7a824460`.
Approved Hugging Face access is required for the first weight download.

```bash
bash scripts/setup-so101-sam3.sh
bash scripts/so101-sam3.sh
# In another terminal:
curl -f http://127.0.0.1:8008/health
```

The environment is isolated under `MAESTRO_SAM3_ROOT` (default user cache).
The service accepts text concepts, normalized point prompts with labels, or
normalized XYWH box prompts on an RGB image. Text/box prompts use SAM 3.1's
detector; point prompts initialize a SAM 3.1 object mask and refine it with the
same model's interactive tracker. Text, point refinement and box extraction
were exercised on the blue bar. The robot currently uses fresh-image text
segmentation, not continuous video tracking.

`segmentation_backend: sam3` selects port 8008. Returned masks retain model,
weight revision and source revision in their NPZ archives. A response without
`backend=SAM3.1` is rejected; no fallback to the old segmentation service occurs.
`workspace_segmentation_prompt: "colored object"` fits the mixed tabletop scene.
Broader `block` prompts can also detect robot parts, so inspect workspace masks
when adapting this prompt. Large static surfaces and duplicate masks are filtered.

Implementation details: use the official multiplex model API directly because
the pinned generic session helper passes an unsupported `offload_state_to_cpu`
argument. Flash Attention 3, compilation and real-valued RoPE optimization are
disabled on this GB10 installation. All checkpoint keys required by the assembled
model must be present before the service reports ready.

The legacy `groundedsam` backend and setup scripts remain only for reproducing
older trials/the original Franka workflow. Its service is stopped locally.
The earlier RGB-only trials below used GroundingDINO + SAM 1; they must not be
relabeled as SAM 3.1 results.

SAM 3.1 validation: `runs/so101-agent/20261113T000632.031278Z` completed
blue-bar grasp, retention lift, placement, release, retreat and home in two
model-generated actor steps without a tool error. Reset maximum error was
0.00114 rad. `segmentation-service-health.json` and mask archives identify
SAM 3.1 and its pinned revisions; the old service was stopped throughout.
`motion-and-recovery.mp4` is 84.3 seconds (inference waits removed). Final RGB
was inspected. The separate reference-depth evaluator passed, but its selected
mask covered a visible side face: it does not measure the complete object.
No simulator depth was supplied to the controller. Relevant tests: 28 passed.

Prompt smoke artifacts are in `runs/so101-sam31-validation/`. An initial direct
point-only call produced no mask; the adapter now uses SAM 3.1 object detection
before interactive point refinement, which returned the blue-bar mask.
`uv pip check` flags NVIDIA's nonstandard `manylinux2014_sbsa` wheel tag for
cuSPARSELt; the installed library is ARM aarch64 and actual CUDA inference passed.


### RGB-only depth (default)

Start the pinned official [Depth Anything V2 metric indoor model](https://huggingface.co/depth-anything/Depth-Anything-V2-Metric-Indoor-Large-hf)
in the existing depth/perception environment (independent of SAM 3.1):

```bash
bash scripts/so101-depth-anything.sh
# In another terminal:
curl -f http://127.0.0.1:8007/health
```

The first start downloads the model. `depth_backend: depth_anything` subscribes
only to RGB, camera calibration and robot state/TF, never the depth topics.
The service receives only an RGB PNG and returns raw metric predictions (not
a normalized visualization). An unavailable service or invalid output fails
explicitly; there is no simulator-depth fallback. Each scan records model,
revision, inference duration and configured metric scale in `*-depth.json`.
`depth_backend: mujoco_sensor` explicitly enables the old depth subscriptions
for reference experiments only.

Monocular metric depth still needs validation at this robot's working distance.
A saved scene took 0.58 seconds to infer; raw object distances were wrong by
1.32–1.49 metres. A scalar fitted only to eight known table-plane pixels reduced
errors at three object pixels to 4.1–8.1 mm, but table residuals reached 23 mm.
This is a single-frame diagnostic, not a grasp-accuracy or generalization test.
The default `metric_scale: 1.0` deliberately does not apply this scene-specific
fit to other cameras. Configure a scale only after calibration against known
geometry; ground-truth object depths must remain evaluation-only.
Diagnostic artifacts are under `runs/so101-monocular-validation/` locally.
Reproduce the fixed-scene diagnostic with the perception environment's Python:

```bash
python scripts/so101-depth-diagnostic.py runs/so101-agent/20261112T170529.323068Z /tmp/so101-depth-diagnostic
```

The script's plane samples are specific to that saved overview; do not reuse
those pixels as calibration for another camera or scene.
Initial live ROS observation passed (about 0.20 seconds per inference), but
depth-only connected components returned zero objects because the inferred
table and objects merged. The semantic segmentation backend now also segments
the workspace before motion. Compact masks define distinct collision objects;
large robot/table/container masks and duplicate detections are rejected. A
separate target mask, disambiguated with Maestro VLM pointing, supplies grasp
geometry. The observed scene produces three collision objects.

The local fixed-overview configuration uses a provisional 0.3028048 scale
fitted from known table-plane pixels. The portable example remains uncalibrated.
A first RGB-only trial (`20261112T232304.234123Z`) grasped the blue bar, lifted it,
transported and released it in the tray, then returned home. This trial used
SAM for the target; workspace-mask collision mapping was added afterward and
is validated separately. The model recovered from an unreachable retreat by
calling reset. The video and final RGB image show actual placement; measured
home error at reset was 0.00117 rad. This single scene does not establish broad
monocular grasp accuracy.

The revised workspace-mask implementation completed a second trial
(`20261112T232858.955747Z`) from the reset mixed scene: three SAM collision
objects, target segmentation, physical grasp/retention lift, transport, release,
retreat and return home. Four model-generated actor steps completed without a
tool error. Home error at reset was 0.00117 rad. The run includes
`ros-node-info.txt` showing no depth subscriptions and `motion-and-recovery.mp4`.
Relevant unit tests: 27 passed (SO101 tools/evaluation/grasp/completion, camera
geometry, mask separation/deduplication, RGB-only depth/no-fallback contracts).

Evaluation limitation: the first trial's estimated-depth placement evaluator
failed because the placed bar was inferred below the support plane. Its failed
`evaluation/` result is preserved. A separate post-trial reference-depth process
confirmed placement; it never supplied depth to the controller. Keep visual,
monocular metric, and simulator reference evaluations distinct. Both completed

### Local Qwen vision model

Set `vlm.provider: local` in `config/maestro.yaml`. The `vlm.local` section in
the example points to `http://127.0.0.1:18082/v1`, model `maestro-qwen-vl`.
No cloud API key is needed. A matching multimodal projector is required in
addition to the language GGUF. Start the server in a separate terminal:

```bash
export LLAMA_SERVER="/path/to/llama.cpp/build/bin/llama-server"
export QWEN_MODEL="/path/to/Qwen3.8-27B-UD-Q4_K_XL.gguf"
export QWEN_MMPROJ="/path/to/mmproj-Qwen3.8-27B-F16.gguf"
bash scripts/so101-vlm.sh
```

The downloaded F16 projector is from
[Unsloth's pinned Qwen3.8 release](https://huggingface.co/unsloth/Qwen3.8-27B-GGUF/blob/1cff334a4a228324d4ee1f76d55d372588f0d556/mmproj-F16.gguf),
SHA-256 `cbb841a9ee0636b2ec172f5bb8df2ea8dfeb01e90fe7c6126581d662a0b4e43e`.
The launcher uses a dedicated localhost port, 16K context and one inference slot.
Maestro sends the current camera images and validates the model's structured
JSON response. Earlier turns keep text, avoiding repeated image accumulation.

On the configured workstation, a user service keeps this server running:

```bash
systemctl --user start maestro-vlm
curl -f http://127.0.0.1:18082/health  # wait for status: ok after model loading
docker compose -f compose.so101.yaml run --rm maestro \
  -i 'グリッパを開いて、画像と関節状態で結果を確認してください'
```

Service diagnostics: `journalctl --user -u maestro-vlm -n 30`.
Stop it with `systemctl --user stop maestro-vlm`. Automatic startup at login is
not enabled. The workstation's unit contains the local SSD/model paths; other
machines can use the environment-variable launcher above.

The local Qwen configuration completed a live MuJoCo gripper-opening trial:
`runs/so101/20261112T112522.141609Z/` contains the generated code, camera images,
joint measurements and model's final assessment. Gripper feedback reached
1.695 rad, with maximum arm joint deviation around 0.015 rad. This validates a
simple natural-language command, not arbitrary manipulation or grasp success.
An additional shoulder-pan trial is recorded in
`runs/so101/20261112T112716.000020Z/`: the measured increment was +0.100000 rad.
An incorrect return-value key in generated verification code was fed back to
Qwen; it corrected the verification without repeating the motion. Other arm
joints drifted by up to 0.0153 rad under the current position controller.

first-plan prompt. `model_reported_complete` is the model's assessment, not an
independent success-rate measurement. Inspect final images and independently

## Coordinates and completion

The six commands and observations are absolute radians in order shoulder_pan,
shoulder_lift, elbow_flex, wrist_flex, wrist_roll, gripper. The folded pose is
`[0, -1.63, 1.43, 1.06, 0, 0.15]`, a model-based approximation of the
[requested photograph](https://storage.googleapis.com/ledge-ai-prd-public-bucket/media/Gpo_K3_HQW_4_AAZ_Xb_d71fcc5429/Gpo_K3_HQW_4_AAZ_Xb_d71fcc5429.jpg).
The simulator starts there. `reset()` plans a checked return; completion is
rejected unless all six measured joints meet tolerance and no object is held.
The shared joint origins and `q_sim = q_real` convention remain unchanged.
Cartesian tools target the finger contact centre in base_link metres.

`execute_grasp` opens, approaches, closes and performs a short retention lift;
it never chooses the destination, places the object or returns home. The model
must compose those steps. Five arm axes cannot realize arbitrary six-axis poses.
The transport checks freshness, subscribers and competing publishers. Commands
use bounded-speed interpolation and model limits. On exit the controller holds
its last target. Actor Python is not sandboxed, as in upstream Maestro. This
backend requires `use_sim_time: true`; no physical robot was commanded.

## Contact solver and independent checks

The simulator uses elliptic friction cones with `impratio=10`, following
[MuJoCo's slip-prevention guidance](https://mujoco.readthedocs.io/en/stable/modeling.html#preventing-slip).
This changes tangential contact impedance, not material friction or robot
geometry. It does not attach objects. `scripts/so101-grasp-probe.py` is an
isolated physics diagnostic: it holds an object, opens the gripper and measures
release. Its simulator-truth measurements are never supplied to the agent.
`--baseline-contact-solver` reproduces the previous pyramidal/impratio=1 setting;
`--contact-solver` selects the manipulation setting explicitly.

After an agent trial has exited, independently check camera placement and home:

```bash
docker compose -f compose.so101.yaml run --rm --entrypoint /bin/bash maestro -c \
  'source /opt/ros/jazzy/setup.bash; /opt/maestro/bin/python -m maestro.so101.agent_evaluate --label "blue elongated box" --output runs/blue-evaluation'
```

The evaluator takes two fresh RGB-D observations, checks the pointed object's
segmented visible extent against the static tray interior, and checks all six
measured home joints. It shares the perception backend, so it is a separate
post-trial measurement, not independent ground-truth sensing.

containing mask. This handles a tray mask that also contains the target. It
raises when no mask contains the point. Release state is preserved if opening
